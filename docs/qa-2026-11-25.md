## 缺陷与修复

### QA2-01 JSON ID 被强制转换，非法输入选择了真实记录或触发异常

关联：FP-CAN-3、FP-SCHED-2，以及 SPEC 的对象 ID/错误响应契约。
最小请求（新候选人，已有 job 1）：

```text
POST /api/candidate/applications
Content-Type: application/json

{"jobId":true}
{"jobId":1.5}
{"jobId":1e309}
```

预期：非法 ID 返回 404，不创建申请；slotId 同理。
修复前：`true`、`1.5`、`1.0` 经 `int(value)` 变为 1，返回 201 并产生申请；`1e309` 被解析为无穷大，触发未处理的 OverflowError。已将原始 `1e400` 缩短为 `1e309`。这没有绕过服务层所有权检查，不把它误报为越权漏洞。

修复：`api.record_id` 仅允许整数或整数字符串，再校验正数和 SQLite 范围；拒绝 bool/float/数组/对象，不转换成其他对象。正常浏览器字符串 ID 保持可用。

回归：`test_json_resource_id_does_not_coerce_or_crash`、`test_missing_json_ids_and_string_ids_preserve_contract`，独立探测和真实 HTTP。实际响应及状态已核对，已修复。

### QA2-02 null/损坏 JSON 被当作空对象，错误请求返回成功

关联：SPEC 的 JSON 对象输入及错误契约；涉及 FP-CAN-1、FP-EMP-1、FP-EMP-2 的更新接口。

最小请求：已登录账号 POST 相应 profile/company/job 更新接口，正文为 `null`、单个 `{` 或空正文，Content-Type 为 application/json。

预期：400，原数据保持不变。修复前：`get_json(silent=True)` 返回 None，再被转换为 `{}`，部分更新接口返回 200。虽然这些最小示例没有改变业务数据，但请求被错误地报告为成功。

修复：消费正文的路由只接受 dict；显式 `{}` 仍是合法的部分更新。logout/delete 等不消费正文的操作没有被额外增加正文要求。

回归：`test_non_object_and_malformed_json_are_rejected` 对三个更新接口验证标量、数组、null、截断和空正文；独立探测与真实 HTTP。已修复。

### QA2-03 同名公司混淆展示资料与可预约时段

关联：FP-EMP-1、FP-CAN-2、FP-SCHED-1/2。公司名不要求唯一；招聘方 ID 才是所有者。

最小复现：

1. 两个招聘方将公司名设成相同文字，公司 description 分别为 OWNER_A_DESCRIPTION / OWNER_B_DESCRIPTION。
2. 两人各建职位和未来时段，候选人只向 A 的职位投递并进入 Interviewing。
3. 打开候选人预约页，再打开 A 的职位详情。

预期：只提供 A 的时段，详情显示 A 的介绍。
修复前：页面按 `company` 字符串过滤，A 的预约卡也列出 B 的时段；bootstrap 的同名公司字典相互覆盖，A 的职位显示 B 的介绍。后端预约 B 时段仍返回 403，因此是可用性和数据展示错误。

修复：live job card 增加 `employerId`，公司记录按稳定 ID 索引；前端用 slot.owner 与 job.employerId 匹配。独立 HTML/demo catalog 保留按名称的兼容路径。同一招聘方的跨职位预约仍可用；非 Interviewing 或已有预订的 application 不返回可用时段。

回归：`test_same_name_companies_remain_distinct_in_candidate_api` 及 `tests/browser/round2.cjs` 两组真实页面/请求/预约断言。修复前两组确实失败，最终两组通过，已修复。

## 变异检查的解释

`tests/acceptance/mutation_check.py` 为每个变异建立隐藏独立副本，编译后运行指定的具名业务用例，解析 pytest XML。语法、收集、环境或超时错误归为 error，不算检出。运行前有未变异 baseline，运行后比较正常 `recruiting/*.py` 的 SHA-256。

17 个非等价变异覆盖：空要求分数、取整、交集、大小写/空白、角色和对象归属、重复申请、有关联记录的删除、Interviewing 资格、未来边界、slot 雇主归属、冲突消息、ID/JSON 输入，以及两端稳定 ID 同分排序。所有均被有意义的断言检出。`100 → (50 + 50)` 在定义域内等价，单独列出并排除于非等价分母。

这是一组人工挑选的有限语义变异，不声称完成全程序变异或达到普遍的“100% 检错率”。本轮没有存活的非等价样本，因而没有通过修改答案来消除存活者。工具额外文件均在忽略目录，不会被 pytest 再次收集，也不会进入 Docker build context。

## 静态检查与运行验证

- 权限：路由 `as_role` + 服务 `require_role/require_owner`；匿名、两候选人、两招聘方矩阵实际请求验证。没有 arbitrary-ID profile API 的设计由直接服务调用检查 owner-only；公开 HTML 壳不包含简历。被拒操作比较全部九张业务表，不只比较行数。
- SQL：用户值均绑定参数；seed 的 f-string 表名来自固定内部表集合，migration 执行仓库受信 SQL。用原有 SQL 元字符绑定记录测试及真实 HTTP 再验证。
- 渲染：检查 HTML 插入位置使用 esc/textContent，实际浏览器注入 script 与 img onerror，检查 DOM 与对话框。没有把仅返回 JSON 字符串当作唯一 XSS 证据；本轮仍不声称穷尽每处 DOM sink。
- 事务：拒绝操作前后比较 users/profiles/skills/companies/jobs/applications/slots/bookings；嵌套事务的内外回滚/提交与恢复均实际执行。真正写锁冲突 503、其他 OperationalError 不被误报为 Slot already booked。
- 对同名公司这一静态疑点先做真实浏览器复现，才归为 QA2-03。未将尚未证实的扫描提示列成缺陷。
