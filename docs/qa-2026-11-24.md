## 已发现并修复的问题

### QA-01 Windows 初始化职位目录失败

影响安装和演示数据初始化，对应 FP-ARCH-1、FP-DOC-1、FP-DOC-3。

原始版本执行 `python -m flask --app recruiting seed --yes`，在中文 Windows 的默认 GBK 编码下触发 `UnicodeDecodeError`。原有两项 seed 测试也因此失败。Docker 的 UTF-8 环境中没有复现这项编码问题。

`recruiting/seed.py` 现在显式按 UTF-8 读取职位 JSON，SQL migration 文件也显式使用 UTF-8。回归由现有 seed 重复执行、数据覆盖和会话失效测试验证。最终 Windows 测试在默认编码下运行。

### QA-02 职位请求被拒绝后仍修改数据库

影响职位创建和编辑的一致性，对应 FP-EMP-2 与 API 文档中的错误响应。

复现创建问题时，以招聘方身份向 `POST /api/employer/jobs` 提交合法 title/body/skills，再加入下列任一字段：

- `type = Unsupported`
- `status = Unsupported`
- 长度 301 的 desc

原始版本返回 400，但数据库多出一条职位。编辑已有职位时同时提交新 title/body/skills 和非法 status，原始版本返回 400，但前面的字段已经改变。

修复后，核心字段和页面附加字段处于同一请求事务中。`recruiting/db.py` 为嵌套服务事务使用 SQLite savepoint，失败时回滚完整请求。四项回归覆盖三种创建失败和一种编辑失败，均验证实际数据库结果。

```powershell
python -m pytest tests/unit/test_acceptance_regressions.py -k rejected_job -q
```

### QA-03 预约 API 绕过原有时间校验

对应 FP-SCHED-1 和 SPEC 中显式时区、完整可表示时间的约定。

原始 `POST /api/employer/slots` 接受没有时区的 `2030-01-02T10:00:00`，按运行机器的本地时区转换。传入 `9999-12-31T23:00:00-23:59` 等 UTC 转换后超范围的时间，则抛出未处理的 OverflowError。

API 现在复用 `scheduling.parse_time`，要求显式时区和完整秒值，超范围输入返回 400。原有合法 `.000Z` 浏览器时间仍可使用。两项回归验证拒绝输入且数据库没有新增时段。

```powershell
python -m pytest tests/unit/test_acceptance_regressions.py -k slot -q
```

### QA-04 新招聘方无法打开首个职位的创建表单

这是阻塞正常流程的 FP-EMP-2 问题。

注册一个没有职位的招聘方，再打开 `/recruiter/jobs?new=1`。原始页面显示空列表，右侧没有创建表单。页面已处于 new 模式，再点击 Post a job 也不能继续。

`recruiter/jobs.html` 的空列表分支现在始终渲染右侧面板。浏览器回归使用新注册招聘方，通过真实表单发布首个职位，然后继续完成投递和预约。

### QA-05 夏令时切换当天的预约转换偏差一小时

对应 FP-SCHED-1、FP-SCHED-2 的时区与预约时间一致性。

原始 `RW.ptToUtc('2027-03-14', 9, 0)` 返回 `2027-03-14T17:00:00.000Z`，对应 Pacific 的 10:00。预期结果为 `16:00Z`，对应用户输入的 09:00。

转换现在根据换算后的实际瞬间重新取 Pacific 时区偏移，并拒绝春季跳过的 02:30 等不存在的时刻。手动表单显示对应错误。页面与文档移除了全年固定 UTC-8 的说法，说明 PST/PDT 的区别。

浏览器回归同时验证春季 09:00、秋季 09:00 和不存在时刻的拒绝。

### QA-06 面试相对日期标签不准确

这是截图复核发现的小问题。原始页面按剩余小时数向上取整，次日早晨的面试可能显示为“两天后”，同日的未来面试则可能显示 Tomorrow。

候选人面试页面现在使用 Pacific 日历日期计算天数，分别显示 Today、Tomorrow 或 In N days。最终 Docker 浏览器回归已通过。完整流程回归增加了次日标签断言。修复前截图保存在 `output/qa/relative-date-before.png`。

## 复跑方法

Windows 的当前工作区可以复用已经安装的虚拟环境。

```powershell
cd D:\CSC4801-qa
D:\CSC4801\.venv\Scripts\python.exe -m pytest -q
```

Docker Engine 位于 WSL，使用下列命令构建和运行测试。

```powershell
wsl -d Ubuntu-22.04 -u root -- docker build -t csc4801-qa-fixed:20261124 /mnt/d/CSC4801-qa
wsl -d Ubuntu-22.04 -u root -- docker run --rm csc4801-qa-fixed:20261124 python -m pytest -q
```

按 INSTALL.md 完成迁移和 seed 后，真实 HTTP 验收可重复创建独立合成账号。

```powershell
D:\CSC4801\.venv\Scripts\python.exe tests/acceptance/http_smoke.py --base-url http://127.0.0.1:8083
```

浏览器验收需要 Node、Playwright 1.62.1 和 Edge。可使用已安装的 Playwright，也可将测试工具安装到忽略目录。

```powershell
npm.cmd install --prefix output/qa-tools playwright@1.62.1
$env:NODE_PATH = "$PWD/output/qa-tools/node_modules"
$env:QA_BASE_URL = "http://127.0.0.1:8083"
$env:QA_OUTPUT = "output/qa/browser-docker"
node tests/browser/acceptance.cjs
```

数据卷复验脚本为 `tests/acceptance/docker_persistence.py`，它通过参数列表调用 Docker，比较重建前后的记录和验证账号，然后恢复演示数据。

本次实际使用 Codex 已有的 Playwright 包与独立浏览器会话，未增加产品运行依赖。QA_BROWSER 可覆盖浏览器可执行文件路径。浏览器脚本会写 results.json 和截图。

本机 WSL 的后台服务会在没有前台会话后停止。本次启动了隐藏的 WSL 保活进程，维持本地 Docker 服务。使用 Docker 时可以保持一个 WSL 会话运行，并通过 `service docker start` 启动引擎。
